# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Sistemas Operacionais (Operating Systems) coursework repository for PUCRS — Escola Politécnica (Prof. Fernando Luís Dotti). `Trabalho1` implements an operating system on top of a simulated virtual machine, built up in progressive phases (memory manager → process manager → scheduler). The professor's original assignment PDFs live in `Trabalho1/enunciado/` and are the authoritative spec — re-read them before implementing a new phase, since the requirements are detailed and easy to misremember (paging semantics, PCB/shell command names, round-robin mechanics).

## Commands

There is no build tool (no Maven/Gradle) and no test framework — this is intentional, matching the plain single-file style the professor provided.

```bash
cd Trabalho1/codigo-fornecido
javac Sistema.java
java Sistema
```

`java Sistema` starts an interactive shell reading commands from stdin (`new`/`rm`/`ps`/`dump`/`dumpM`/`exec`/`execAll`/`traceOn`/`traceOff`/`exit` — see the `Shell` entry under Architecture) — it blocks waiting for input. A background scheduler thread starts at the same time and runs continuously for the life of the process: any `new` process is picked up and run automatically (round-robin, `delta`-instruction time slices), with no need to `exec` it. To test non-interactively, pipe a script of commands: `java Sistema < roteiro.txt` (put scratch roteiro files outside the repo, e.g. in a scratchpad dir — they're not test fixtures to commit). Since execution is now continuous and concurrent with the shell, a piped script needs an `execAll` (blocks until the system has no processes left) wherever the test depends on prior processes having actually finished before the next command runs. CPU instruction trace is off by default; toggle with `traceOn`/`traceOff` from the shell.

Validation is manual: run it (interactively or via a piped command script) and read the console output (trace of executed instructions when tracing is on, memory dumps, `SYSCALL`/interrupt messages, PCB/`ps` listings). Compiled `.class` files are gitignored — delete them locally after testing (`rm -f Sistema*.class`) rather than committing them.

## Architecture

Everything lives in one file, `Trabalho1/codigo-fornecido/Sistema.java`, as nested classes inside the top-level `Sistema` class. This is a deliberate style choice (matches the professor's own code and keeps submission simple), not something to refactor into multiple files/packages.

**HW layer (simulated hardware — the part that must never change program semantics):**
- `Memory` / `Word`: memory is a flat array of `Word` (`opc`, `ra`, `rb`, `p`). `Opcode.DATA` marks a data word instead of an instruction.
- `CPU`: has `pc`, `ir`, 8 general registers (`reg[0..7]`) plus `reg[8]`/`reg[9]` reserved for I/O syscall parameters, and an `Interrupts` flag. `run()` is the fetch-execute loop; `setContext(PCB pcb)` primes it to start/resume a process — see the context-switching note below, since `reg` is not copied but aliased to `pcb.reg`.
- `Programs`: a fixed set of hand-assembled `Word[]` programs (`fatorialV2`, `fibonacci10v2`, `PC` bubble sort, etc.) used as test payloads. **Never modify these images** — the assignment explicitly requires programs to run unmodified; only the loading/execution machinery around them changes between phases.

**SW layer (the OS being built, inside the `SO` class):**
- `GerenteMemoria` (Fase 1A, done): paging-based memory manager. `aloca(nroPalavras)` returns an `int[] tabelaPaginas` (page → frame) or `null` if there isn't enough free memory — a deliberate deviation from the enunciado's suggested `Boolean aloca(OUT tabelaPaginas)` signature, since a nullable return is more idiomatic in Java and has the same call-site semantics. `desaloca(tabelaPaginas)` frees the frames.
- Address translation lives in `CPU.traduz(enderecoLogico)` (not in `GerenteMemoria`) — it converts a logical address to physical via the *currently running process's* `tabelaPaginas` (set by `setContext`), and raises `intEnderecoInvalido` if the page is outside that table. This replaced the original HW-only `legal(e)` bounds check. Every memory access in `CPU.run()` goes through `traduz()` first — when adding new instructions or touching this loop, remember indirect-jump opcodes (`JMPIM`/`JMPIGM`/`JMPILM`/`JMPIEM`) also read memory via `ir.p` and must be translated too (three of them had no bounds check at all in the professor's original code — this was fixed as part of 1A since untranslated paging access would otherwise corrupt memory or throw `ArrayIndexOutOfBoundsException`).
- `SysCallHandling.handle()`'s write case also translates `reg[9]` via `hw.cpu.traduz(...)` before indexing physical memory, since it holds a logical address — easy to forget when extending syscalls (e.g. adding the read case, still an empty stub).
- `Utilities.carregaPaginado(imagem, tabelaPaginas)` copies a program's words into their assigned frames (page `i/tamPg`, offset `i%tamPg`); `dumpLogico` mirrors that translation for inspecting a process's memory as it "sees" it. The old contiguous `loadProgram`/`loadAndExec` were removed — all loading is paginated now.
- Cross-inner-class private access (e.g. `SysCallHandling` calling the `private` `CPU.traduz`, or reading `hw.cpu.pc`/`hw.cpu.reg`) is normal here: Java allows sibling inner classes of the same enclosing class to reach each other's private members. This codebase relies on that instead of getters — keep following that pattern rather than introducing accessors.
- `Sistema(tamMem, tamPg, delta)` / `HW(tamMem, tamPg, delta)`: all three must stay configurable — the assignment requires the system to work across different memory/page sizes and time-slice lengths. `main()` currently instantiates one config (1024/8, delta=5); Fase 1A's automated two-config demo was retired once the shell (1B) made the entry point interactive — if you need to prove a different config works, temporarily edit the `main()` call.
- `GerenteProcessos` (GP): owns the process table (`todosProcessos`, the `prontos` ready queue, and the `running` pointer). `criaProcesso(Word[] imagem)` calls `GerenteMemoria.aloca` + `Utilities.carregaPaginado`, creates a `PCB`, and returns its `id` (or `-1` on allocation failure) — deviates from the enunciado's `boolean` signature the same way `GerenteMemoria.aloca` does; resolving a program *name* to its `Word[]` image is the `Shell`'s job (via `Programs.retrieveProgram`), not GP's, so "unknown program name" and "out of memory" get distinct error messages. Since Fase 1C, **every GP method is `synchronized`** (lock on the GP instance itself) and methods returning collections (`getTodosProcessos`) return defensive copies — two threads (Shell and the scheduler, see below) touch this state concurrently now. GP does **not** touch the CPU directly — `iniciaExecucao`/`preemptaProcessoEmExecucao`/`finalizaProcessoEmExecucao` just flip `PCB.estado`/queues/the `running` pointer; `Escalonador` is what calls `hw.cpu.setContext(...)`, matching the reference architecture diagram (doc 5) where GP and the CPU rotina are separate boxes.
- `Escalonador.escalona()`: pulls the next `PRONTO` PCB off GP's ready queue (`proximoPronto()`), marks it running, and calls `hw.cpu.setContext(pcb)`. It has no lock of its own — it's only ever invoked from one thread at a time (the background scheduler thread, directly or transitively via `ih.handle()`/`sysCall.stop()` which run *inside* `hw.cpu.run()` on that same thread), so correctness comes entirely from GP's own synchronized methods.
- **Context switching (Fase 1C)**: `PCB` now carries `pc` and `reg` (an `int[10]`, mirroring `CPU.reg`). The key trick: `CPU.setContext(pcb)` does `reg = pcb.reg` — an **aliasing assignment**, not a copy. While a process is running, `CPU.reg` *is* `pcb.reg`; every instruction that touches a register is already, transparently, writing into that process's saved context. Only `pc` is a plain CPU field, so it's the one thing `CPU.salvaContexto(pcb)` has to copy back explicitly when a process is preempted. Don't "fix" this into an explicit register copy — it would be redundant and the aliasing is intentional.
- **Round-robin timer**: `CPU` counts instructions since the last `setContext` (`contadorDelta`); once it reaches `delta`, `irpt` is set to the new `Interrupts.intTimer` value, reusing the exact same interrupt-check block that already existed for real errors. `InterruptHandling.handle()` branches on it: `intTimer` saves context and calls `gp.preemptaProcessoEmExecucao()` (process survives, goes to the back of `prontos`); any other interrupt calls `gp.finalizaProcessoEmExecucao()` (process is gone for good). Both branches end with `escalonador.escalona()`. `SysCallHandling.stop()` follows the same finalize-then-escalona pattern for STOP. This is also why `SO`'s constructor had to be reordered: `gm`/`gp`/`escalonador` now have to exist *before* `ih`/`sc` are constructed, since the handlers depend on them.
- **Continuous background execution (Fase 1C, "funcionamento contínuo")**: confirmed with the user as an always-on design, not an opt-in mode. `ThreadEscalonador` (a daemon `Thread`, started in `Shell`'s constructor) loops forever: if no process is running, try `escalona()`; if one is now set, call `hw.cpu.run()` for one slice; otherwise sleep ~20ms and retry. This is deliberately simple polling, not a `wait`/`notify` or semaphore handshake (doc 5's more elaborate `semaSch`/`semaCPU` diagram) — good enough to satisfy the doc's literal "no mínimo duas threads" bar without that extra machinery. Because of this, **`exec <id>` and `execAll` changed meaning from Fase 1B**: `exec` no longer touches the CPU (it would race with the scheduler thread) and is now purely informational (prints the process's current state); `execAll` no longer drives execution itself — it just polls `gp.getTodosProcessos()` until empty, i.e. it blocks until whatever the background thread is already doing finishes. A process created with `new` starts running on its own; no command is needed to kick it off.
- **STOP/error finalization changed too**: as of Fase 1C, `finalizaProcessoEmExecucao()` fully deallocates (memory + PCB) the instant a process stops or errors — matching doc 4 section 2.2. There is no more `TERMINADO`-but-kept-around state like in Fase 1B: a finished process simply disappears from `ps`/`dump`. `rm <id>` also changed shape: `GerenteProcessos.tentaRemover(id)` does the existence-check-and-removal as one atomic `synchronized` method (replacing 1B's separate check+`desalocaProcesso`) specifically to close a race where the scheduler thread could promote a process to `RODANDO` between the check and the removal; it also now refuses to remove a `RODANDO` process (not safe to reclaim its frames mid-instruction), returning a message instead of throwing.
- `Shell` is the whole interactive front end (`new`/`rm`/`ps`/`dump`/`dumpM`/`exec`/`execAll`/`traceOn`/`traceOff`/`exit`), reading `System.in` with a `Scanner`, one command per line, tokenized on whitespace. Every command method guards against missing/non-numeric args and unknown ids/program names by printing an error and returning — a malformed command must never throw and kill the loop. `Sistema.run()` is just `new Shell(hw, so, progs).loop()`; the `Shell` constructor is what starts `ThreadEscalonador`, and `exit` stops it (`threadEscalonador.encerra()`) before the shell prints its goodbye and returns.
- `Programs.retrieveProgram(String pname)` had a latent bug fixed as part of 1B: it compared names with `==` instead of `.equals(...)`. That "worked" only because every prior call site passed a string literal (Java interns those), so both sides happened to be the same object; it broke for real the moment a name arrived from user input (`Scanner`/`split` produce non-interned strings). If similar string comparisons show up elsewhere, assume `==` is wrong.
- Accepted, documented race: `dump <id>` reads `pcb.reg`/`pcb.estado` without taking any lock, so dumping a currently-`RODANDO` process can show a torn (but not corrupt — individual `int` reads/writes are atomic in the JVM) snapshot of its registers, since that array is the same one the scheduler thread may be mutating concurrently. This is treated as an acceptable debug-dump limitation, not a bug to fix with extra locking.

## Phase status

All three phases of Trabalho 1 are implemented: HW (provided), 1A (`87c08bd`, paging memory manager), 1B (`23bc32e`, process manager + shell), and 1C (round-robin scheduler with continuous background execution). Doc 5's third reference diagram ("multithreaded+IO", adding a Console thread and blocked-process queue for I/O-triggered preemption) goes beyond what docs 1-4 ask for and was treated as context/preview, not a requirement — the `SYSCALL` read case (`reg[8]==1`) is still an empty stub, unchanged since the professor's original code.

## Working conventions for this repo

- Read the relevant `Trabalho1/enunciado/0N-*.pdf` before changing behavior in an area it covers — the requirements are detailed and easy to misremember (paging semantics, PCB/shell command names, round-robin mechanics).
- No automated tests are used — treat a successful `javac` + a `java Sistema` run whose console output matches expected program results (e.g. factorial/Fibonacci values, correct page tables, interleaved round-robin trace, no unexpected interrupts or exceptions) as the verification bar.
- Never `git commit` or `git push` without the user explicitly asking in that turn.
